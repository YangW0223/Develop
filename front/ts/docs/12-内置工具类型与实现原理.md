# 12. 内置工具类型与实现原理

TypeScript 标准库提供了一批全局可用的工具类型，用来对已有类型进行常见变换。它们本身只参与编译期类型检查，不会生成 JavaScript，也不会在运行时验证数据。

本章会同时讲三件事：

1. 工具类型解决什么问题。
2. 它大致如何用 TypeScript 类型语法实现。
3. 它有哪些边界，实际项目中什么时候不应该使用它。

示例中的 `My...` 类型是为了展示原理，不建议在项目中重复定义同名工具。实际开发优先使用标准库提供的名称。

## 1. 工具类型的共同基础

大多数工具类型由下面几种能力组合而成：

- `keyof T`：得到类型 `T` 的键联合。
- `T[K]`：取得键 `K` 对应的属性类型。
- `[K in keyof T]`：遍历属性，也就是映射类型。
- `T extends U ? X : Y`：根据条件选择结果。
- `never`：从联合类型中删除不需要的成员。
- `infer`：从已有结构中提取内部类型。

例如，下面的工具把所有属性变成可选：

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
```

阅读任何工具类型时，可以按“遍历哪些键、修改什么修饰符、是否进行条件判断、是否提取内部类型”的顺序拆解。

## 2. 属性修饰工具

### 2.1 `Partial<T>`：全部属性可选

```ts
interface Todo {
  title: string;
  description: string;
  completed: boolean;
}

function updateTodo(todo: Todo, patch: Partial<Todo>): Todo {
  return { ...todo, ...patch };
}

const todo: Todo = {
  title: "整理桌面",
  description: "清理不需要的文件",
  completed: false,
};

updateTodo(todo, { completed: true });
```

实现原理：

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
```

常见场景是更新对象、配置覆盖和 PATCH 请求参数。它是浅层的：

```ts
type State = {
  user: { name: string; age: number };
};

type PartialState = Partial<State>;
// user 可以缺少，但如果存在，name 和 age 仍然必填
```

不要把 `Partial<T>` 当作深层可选。需要深层效果时应明确定义 `DeepPartial`，并考虑数组、函数和 `Date` 等特殊对象。

### 2.2 `Required<T>`：全部属性必填

```ts
interface Options {
  cache?: boolean;
  timeout?: number;
}

const options: Required<Options> = {
  cache: true,
  timeout: 5000,
};
```

实现原理是用 `-?` 移除可选修饰符：

```ts
type MyRequired<T> = {
  [K in keyof T]-?: T[K];
};
```

它常用于“外部配置可选、内部配置已补全”的阶段：

```ts
function withDefaults(input: Options): Required<Options> {
  return {
    cache: input.cache ?? true,
    timeout: input.timeout ?? 5000,
  };
}
```

`Required<T>` 不会自动提供缺失值，只会要求调用者把值补齐。

### 2.3 `Readonly<T>`：属性不可重新赋值

```ts
type User = {
  id: number;
  name: string;
};

const user: Readonly<User> = { id: 1, name: "小明" };
// user.name = "小红"; // ❌
```

实现原理：

```ts
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};
```

它同样是浅层的：

```ts
type Config = Readonly<{
  nested: { enabled: boolean };
}>;

const config: Config = { nested: { enabled: true } };
config.nested.enabled = false; // 合法：nested 内部没有被递归只读
```

`Readonly<T>` 是编译期限制，不等于运行时冻结。需要运行时冻结时使用 `Object.freeze`，但也要注意 `Object.freeze` 默认同样是浅层的。

### 2.4 `Pick<T, K>`：保留指定属性

```ts
type User = {
  id: number;
  name: string;
  email: string;
  passwordHash: string;
};

type UserPreview = Pick<User, "id" | "name">;
// { id: number; name: string }
```

实现原理：

```ts
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};
```

`K extends keyof T` 是关键约束：选择不存在的键会报错。

```ts
// type Invalid = Pick<User, "id" | "phone">; // ❌ phone 不属于 User
```

### 2.5 `Omit<T, K>`：排除指定属性

```ts
type PublicUser = Omit<User, "passwordHash">;
```

实现原理：先从全部键中排除 `K`，再交给 `Pick`：

```ts
type MyExclude<T, U> = T extends U ? never : T;

type MyOmit<T, K extends keyof T> = MyPick<T, MyExclude<keyof T, K>>;
```

也可以直接使用交叉类型和 `Omit` 组合：

```ts
type CreateUserInput = Omit<User, "id" | "passwordHash"> & {
  password: string;
};
```

如果新增字段后某些接口不应自动暴露它，显式使用 `Pick` 往往比到处 `Omit` 更安全，因为它采用允许列表而不是排除列表。

## 3. 键值映射工具

### 3.1 `Record<K, T>`：建立键到值的映射

```ts
type Role = "admin" | "editor" | "viewer";

type RoleLabel = Record<Role, string>;

const labels: RoleLabel = {
  admin: "管理员",
  editor: "编辑者",
  viewer: "只读用户",
};
```

由于键是有限联合，漏写任何一个键都会报错。实现原理：

```ts
type MyRecord<K extends PropertyKey, T> = {
  [P in K]: T;
};
```

动态字典也可以使用 `Record<string, T>`，但它无法保证运行时一定有某个具体键：

```ts
type UserById = Record<string, User>;
```

如果查询结果可能没有对应项，函数返回值应包含 `undefined`：

```ts
function findUser(users: UserById, id: string): User | undefined {
  return users[id];
}
```

### 3.2 `Readonly<Record<...>>` 组合

工具类型可以组合，形成更准确的配置：

```ts
type Feature = "search" | "export" | "darkMode";
type FeatureConfig = Readonly<Record<Feature, boolean>>;

const features: FeatureConfig = {
  search: true,
  export: false,
  darkMode: true,
};
```

## 4. 联合类型工具

### 4.1 `Exclude<T, U>`：从联合中排除成员

```ts
type Status = "idle" | "loading" | "success" | "error";
type FinishedStatus = Exclude<Status, "idle" | "loading">;
// "success" | "error"
```

实现原理：

```ts
type MyExclude<T, U> = T extends U ? never : T;
```

它依赖分布式条件类型：联合的每个成员分别判断，不符合的成员变成 `never`。

### 4.2 `Extract<T, U>`：保留可赋值成员

```ts
type Event =
  | { kind: "click"; x: number; y: number }
  | { kind: "keypress"; key: string }
  | { kind: "submit"; formId: string };

type MouseEvent = Extract<Event, { kind: "click" }>;
// { kind: "click"; x: number; y: number }
```

实现原理：

```ts
type MyExtract<T, U> = T extends U ? T : never;
```

`Extract` 的判断是“可赋值”，不要求两个对象类型完全相同；只要成员拥有目标结构即可。

### 4.3 `NonNullable<T>`：排除 `null` 和 `undefined`

```ts
type MaybeUser = User | null | undefined;
type ExistingUser = NonNullable<MaybeUser>;
// User
```

实现原理：

```ts
type MyNonNullable<T> = T extends null | undefined ? never : T;
```

它不会验证一个变量当前是否有值，只是构造一个不允许空值的类型。使用前仍应先做运行时判断。

## 5. 函数相关工具

### 5.1 `Parameters<T>`：取得参数元组

```ts
function createUser(name: string, age: number, active = true) {
  return { name, age, active };
}

type CreateUserParameters = Parameters<typeof createUser>;
// [name: string, age: number, active?: boolean]
```

实现原理：

```ts
type MyParameters<T> = T extends (...args: infer Args) => unknown
  ? Args
  : never;
```

它适合包装已有函数，确保代理函数的参数与原函数同步：

```ts
function loggedCall<F extends (...args: any[]) => any>(
  fn: F,
  ...args: Parameters<F>
): ReturnType<F> {
  console.log("调用函数", args);
  return fn(...args);
}
```

上例为简洁使用了 `any`。在基础库中可以根据项目的严格程度改进函数约束，并注意参数方差。

### 5.2 `ReturnType<T>`：取得返回类型

```ts
type CreatedUser = ReturnType<typeof createUser>;
// { name: string; age: number; active: boolean }
```

实现原理：

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer Result
  ? Result
  : never;
```

异步函数的返回类型是 Promise：

```ts
async function loadUser(): Promise<User> {
  return { id: 1, name: "小明" };
}

type Raw = ReturnType<typeof loadUser>; // Promise<User>
type Data = Awaited<Raw>;               // User
```

### 5.3 `ConstructorParameters<T>` 与 `InstanceType<T>`

```ts
class UserService {
  constructor(
    private readonly baseUrl: string,
    private readonly timeout: number,
  ) {}
}

type ConstructorArgs = ConstructorParameters<typeof UserService>;
// [baseUrl: string, timeout: number]

type Service = InstanceType<typeof UserService>;
// UserService 实例类型
```

两者接收的是构造函数类型，因此要写 `typeof UserService`，而不是实例类型 `UserService`。

简化实现：

```ts
type MyConstructorParameters<T> =
  T extends abstract new (...args: infer Args) => unknown
    ? Args
    : never;

type MyInstanceType<T> =
  T extends abstract new (...args: any[]) => infer Instance
    ? Instance
    : never;
```

`abstract new` 允许抽象类构造签名参与类型计算；若只需要普通类，也可以使用 `new`。

## 6. `Awaited<T>`：递归解除异步包装

```ts
type A = Awaited<Promise<string>>;                 // string
type B = Awaited<Promise<Promise<number>>>;        // number
type C = Awaited<boolean | Promise<number>>;      // boolean | number
```

它模拟 `await` 和 Promise `.then()` 的结果，能够递归解除嵌套 Promise，并对联合类型分别处理。一个用于理解原理的简化版本如下：

```ts
type MyAwaited<T> =
  T extends null | undefined
    ? T
    : T extends object & {
        then(
          onfulfilled: infer F,
          ...args: infer _Rest
        ): unknown;
      }
      ? F extends (value: infer Value, ...args: any[]) => unknown
        ? MyAwaited<Value>
        : never
      : T;
```

标准实现还要处理 thenable 的错误形态和递归细节，所以不要把上面的简化版本复制到生产工具库。异步 API 的类型通常写成 `Promise<Result<T>>`，调用处再使用 `Awaited` 或 `await` 得到内部数据。

## 7. `NoInfer<T>`：阻止某个位置参与推断

泛型函数有时会从多个参数推断同一个类型，导致一个本应被检查的参数反过来扩大类型范围：

```ts
function createStreetLight<C extends string>(
  colors: C[],
  defaultColor?: C,
): void {}

createStreetLight(["red", "yellow", "green"], "blue");
// 某些推断场景下，defaultColor 会参与 C 的推断
```

使用 `NoInfer<C>` 可以表达“`C` 由第一个参数推断，第二个参数只负责检查”：

```ts
function createStreetLight<C extends string>(
  colors: C[],
  defaultColor?: NoInfer<C>,
): void {}

createStreetLight(["red", "yellow", "green"], "red");
// createStreetLight(["red", "yellow", "green"], "blue"); // ❌
```

它适合默认值、回退值和配置之间的约束。`NoInfer` 是编译器提供的特殊工具，不能用普通条件类型完全等价地实现；历史上常见的元组技巧只是近似方案：

```ts
// 旧代码中可能见到的近似写法，不如内置 NoInfer 清晰
type NoInferLike<T> = [T][T extends any ? 0 : never];
```

如果项目 TypeScript 版本较旧而没有 `NoInfer`，应先确认编译器版本，再决定是否使用兼容写法或升级版本。

## 8. `this` 相关工具

### 8.1 `ThisParameterType<T>`

取得函数显式声明的 `this` 参数：

```ts
function handle(this: HTMLButtonElement, event: MouseEvent): void {
  this.disabled = true;
  console.log(event.type);
}

type Context = ThisParameterType<typeof handle>;
// HTMLButtonElement
```

没有显式 `this` 参数时，结果通常是 `unknown`。

简化实现：

```ts
type MyThisParameterType<T> =
  T extends (this: infer This, ...args: any[]) => any
    ? This
    : unknown;
```

### 8.2 `OmitThisParameter<T>`

从函数类型中移除 `this` 参数，得到普通可调用函数：

```ts
type Callback = OmitThisParameter<typeof handle>;
// (event: MouseEvent) => void
```

简化实现：

```ts
type MyOmitThisParameter<T> =
  unknown extends ThisParameterType<T>
    ? T
    : T extends (this: any, ...args: infer Args) => infer Result
      ? (...args: Args) => Result
      : T;
```

### 8.3 `ThisType<T>`

`ThisType<T>` 不会创建一个新结构，它是一个标记，用来改变对象字面量方法中 `this` 的上下文。通常与 `noImplicitThis` 和 `satisfies` 一起使用：

```ts
type Store<Data, Methods> = {
  data: Data;
  methods: Methods & ThisType<Data & Methods>;
};

type Counter = {
  count: number;
};

const counter: Store<Counter, {
  increment(): void;
}> = {
  data: { count: 0 },
  methods: {
    increment() {
      // ThisType 让这里的 this 拥有 count 和 increment
      this.count += 1;
    },
  },
};
```

`ThisType<T>` 主要影响上下文类型推断，不会在运行时做任何事情，也不能像普通泛型那样通过 `T` 取出一个具体值类型。

## 9. 内置字符串操作类型

TypeScript 提供四个内置字符串类型工具：

```ts
type Upper = Uppercase<"hello">;       // "HELLO"
type Lower = Lowercase<"HELLO">;       // "hello"
type Capital = Capitalize<"userName">; // "UserName"
type Uncapital = Uncapitalize<"UserName">; // "userName"
```

它们常和模板字面量类型、键重映射组合：

```ts
type Events = "save" | "cancel";

type Handlers = {
  [K in Events as `on${Capitalize<K>}`]: () => void;
};

// {
//   onSave: () => void;
//   onCancel: () => void;
// }
```

这些类型由编译器内置实现，用户不能用普通 TypeScript 类型语法完全复刻其大小写转换算法。它们对字面量字符串最有用；如果输入是普通 `string`，结果通常也只是 `string`。

## 10. 常用工具的组合案例

### 10.1 表单编辑类型

创建表单时不允许提交服务端生成的字段，并允许部分字段更新：

```ts
type Article = {
  id: number;
  title: string;
  content: string;
  createdAt: Date;
  updatedAt: Date;
};

type ArticleForm = Omit<Article, "id" | "createdAt" | "updatedAt">;
type ArticlePatch = Partial<ArticleForm>;
```

`Omit` 定义允许编辑的边界，`Partial` 定义 PATCH 的部分更新语义。

### 10.2 从 API 函数推导调用器

```ts
async function fetchUser(id: number, includePosts = false): Promise<User> {
  return { id, name: includePosts ? "小明（含文章）" : "小明" };
}

async function callWithLog<F extends (...args: any[]) => any>(
  fn: F,
  ...args: Parameters<F>
): Promise<Awaited<ReturnType<F>>> {
  console.log("args:", args);
  return await fn(...args);
}

const user = await callWithLog(fetchUser, 1, true);
// user 是 User
```

这里 `Parameters` 保证参数同步，`ReturnType` 取得 Promise 返回值，`Awaited` 得到真正的数据类型。

### 10.3 从状态联合中提取某个分支

```ts
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };

type SuccessState = Extract<
  RequestState<User[]>,
  { status: "success" }
>;

type SuccessData = SuccessState["data"]; // User[]
```

`Extract` 先筛出联合成员，再通过索引访问类型拿到分支数据。

## 11. 工具类型不是运行时校验

```ts
type User = {
  id: number;
  name: string;
};

const raw: unknown = JSON.parse('{"id":"错误","name":123}');
const user = raw as User;
```

即使 `user` 的静态类型是 `User`，真实值仍可能不符合结构。`Partial`、`Required`、`Pick` 等工具只改变编译器的看法，不会检查 JSON、接口响应或用户输入。

可信流程应当是：

```text
unknown → 运行时校验 → 通过校验的业务类型 → 工具类型变换
```

小结构可以手写类型守卫，复杂结构可以使用运行时 schema 库。不要用 `as` 把未验证的外部数据伪装成安全类型。

## 12. 常见边界和选择建议

| 需求 | 推荐工具 | 注意事项 |
| --- | --- | --- |
| 部分更新 | `Partial<T>` | 浅层；不代表字段值有效 |
| 补全默认配置 | `Required<T>` | 只要求存在，不负责生成值 |
| 只读视图 | `Readonly<T>` | 浅层；不等于运行时冻结 |
| 公开字段 | `Pick<T, K>` | 允许列表通常比排除列表更安全 |
| 排除字段 | `Omit<T, K>` | 新增字段时要重新审查暴露面 |
| 有限键映射 | `Record<K, V>` | 联合键能检查是否漏项 |
| 联合筛选 | `Extract`、`Exclude` | 依赖可赋值关系，不是字符串匹配 |
| 去除空值 | `NonNullable<T>` | 不做运行时空值判断 |
| 复用函数签名 | `Parameters`、`ReturnType` | 重载函数取到的通常是最后一个签名 |
| Promise 结果 | `Awaited<T>` | 只描述类型，不会等待值 |
| 控制泛型推断 | `NoInfer<T>` | 需要较新 TypeScript 版本 |
| 生成事件名 | `Capitalize` 等 | 普通 `string` 无法产生具体联合 |

## 13. 自定义工具的检查清单

写一个新工具类型前，先问：

1. 标准库是否已经提供了同样能力？
2. 它是浅层还是深层？调用者是否明确知道这一点？
3. 联合类型是否会触发分布式条件类型？
4. `any`、`unknown` 和 `never` 输入时结果是否合理？
5. 键是字符串、数字还是 `symbol`？是否需要 `PropertyKey`？
6. 错误提示是否仍然能被团队成员读懂？
7. 类型变复杂后，是否真的减少了业务代码重复？

## 14. 练习

### 练习一：深层工具

实现 `DeepRequired<T>`，把嵌套对象的可选属性递归变成必填，并思考数组和函数应如何处理。

### 练习二：可写字段

实现 `Mutable<T>`，移除所有属性的 `readonly`：

```ts
type Mutable<T> = {
  -readonly [K in keyof T]: T[K];
};
```

再思考如何只移除指定键的只读修饰符。

### 练习三：函数结果解包

实现 `AsyncResult<F>`：当 `F` 是返回 `Promise<T>` 的函数时，结果为 `T`；否则为 `ReturnType<F>`。

```ts
type AsyncResult<F extends (...args: any[]) => any> =
  Awaited<ReturnType<F>>;
```

### 练习四：事件处理器

将下面的事件映射生成 `onLogin`、`onLogout` 和 `onError`：

```ts
type Events = {
  login: { userId: string };
  logout: undefined;
  error: { message: string; code: number };
};
```

要求有 payload 的事件接收一个参数，没有 payload 的事件不接收参数。

## 小结

常用内置工具并不是一堆孤立的魔法：

```text
Partial / Required / Readonly
    ↓ 属性修饰符映射
Pick / Omit / Record
    ↓ 键集合映射
Exclude / Extract / NonNullable
    ↓ 分布式条件类型 + never
Parameters / ReturnType / InstanceType
    ↓ infer 提取函数结构
Awaited / NoInfer / ThisType
    ↓ 异步、推断控制和 this 上下文
```

理解这些实现模式后，遇到新工具类型时可以自己推导它的行为；实际项目中则优先使用标准库名称，并把自定义工具限制在确实能提升业务表达力的范围内。
