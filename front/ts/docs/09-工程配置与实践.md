# 09. 工程配置与实践

## 1. `tsconfig.json` 的职责

`tsconfig.json` 告诉编译器检查哪些文件、采用哪套 JavaScript/模块规则，以及启用哪些严格检查。

一个适合现代前端项目的起点：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noEmit": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

框架脚手架通常会生成合适配置，应在理解构建环境后调整，不要直接覆盖。

## 2. 关键选项

### `strict`

开启一组严格检查，包括严格空值、函数参数等。新项目应从一开始开启，后期开启的迁移成本更高。

### `noUncheckedIndexedAccess`

数组或未知键访问会包含 `undefined`：

```ts
const names: string[] = [];
const first = names[0]; // string | undefined
```

它让类型更符合真实运行行为。

### `exactOptionalPropertyTypes`

区分“属性不存在”和“属性存在但值为 `undefined`”：

```ts
type Options = { theme?: "dark" | "light" };
const options: Options = {};
// options.theme = undefined; // 开启后报错，除非类型显式包含 undefined
```

### `skipLibCheck`

跳过 `.d.ts` 内部的类型检查以提升速度，但你的代码使用这些声明时仍会被检查。它不等于跳过整个项目的类型检查。

## 3. 类型检查和代码转换可能是两件事

Vite、esbuild、Babel 等可以快速移除 TypeScript 语法，却可能不执行完整类型检查。因此 CI 通常要单独运行：

```bash
tsc --noEmit
```

再配合 ESLint 检查未使用变量、Promise 误用等类型系统之外或需要类型信息的规则。

## 4. 项目边界使用 `unknown`

不可信数据包括：

- `JSON.parse` 的结果和 HTTP 响应。
- `localStorage` 中的历史数据。
- URL 参数、表单输入和消息事件。
- 第三方 SDK 回调。

推荐流程：

```text
外部 unknown → 运行时解析/校验 → 可信业务类型 → 内部逻辑
```

不要直接把接口结果断言为业务类型：

```ts
// 危险：没有运行时验证
const user = (await response.json()) as User;
```

小模型可手写类型守卫，复杂模型使用 Zod、Valibot、ArkType 等运行时 schema 库，并从 schema 推断 TypeScript 类型，减少两份定义不同步的问题。

## 5. 错误处理

捕获到的值不一定是 `Error`：

```ts
function errorMessage(error: unknown): string {
  if (error instanceof Error) return error.message;
  return String(error);
}

try {
  throw new Error("网络错误");
} catch (error: unknown) {
  console.error(errorMessage(error));
}
```

可预期的业务失败可以用可辨识联合表达，而不是全部抛异常：

```ts
type SaveResult =
  | { ok: true; id: string }
  | { ok: false; reason: "invalid" | "conflict" };
```

异常适合无法在当前层恢复、会中断正常流程的错误；返回结果适合调用者应当明确处理的业务分支。

## 6. 避免滥用断言和 `any`

遇到类型错误时按顺序思考：

1. 数据模型是否真实反映了运行情况？
2. 是否漏掉了空值或某个联合成员？
3. 能否通过判断收窄类型？
4. 第三方声明是否准确？
5. 只有证据充分时才使用局部断言，并注释原因。

`@ts-ignore` 会无条件隐藏下一行错误。临时兼容时优先 `@ts-expect-error`，因为错误消失后编译器会提醒删除它：

```ts
// @ts-expect-error 旧版 SDK 声明缺少 runtimeOnlyOption，升级后删除
legacySdk.start({ runtimeOnlyOption: true });
```

## 7. 类型测试与运行测试

类型检查不能验证业务计算结果：

```ts
function add(a: number, b: number): number {
  return a - b; // 类型正确，业务逻辑错误
}
```

项目需要两类保障：

- `tsc --noEmit` 验证类型契约。
- Vitest、Jest 等验证运行行为。

公共类型工具还可以用 `tsd`、`expect-type` 或 `@ts-expect-error` 编写类型层面的测试。

## 8. 推荐目录思路

```text
src/
├── domain/       # 与框架无关的业务类型和规则
├── services/     # 请求、存储等外部能力
├── features/     # 按功能组织的应用代码
├── shared/       # 真正跨功能复用的工具
└── main.ts       # 入口和依赖组装
```

目录应围绕当前项目规模演化。不要因为学习到某种架构，就在小项目里预先创建大量空层。

## 9. 渐进迁移 JavaScript

可采用以下顺序：

1. 开启 `allowJs`，先把 JavaScript 纳入项目。
2. 对关键模块使用 JSDoc 或改名为 `.ts`。
3. 在边界处补类型，逐步减少隐式 `any`。
4. 开启更严格选项并分批修复。
5. 用测试保护行为，避免迁移时顺手改变逻辑。

类型改造和业务重构分开进行，问题更容易定位。

## 10. 本章检查清单

- 项目是否启用了 `strict`？
- CI 是否独立运行类型检查？
- 外部数据是否先校验再使用？
- 是否能用 `unknown` 替代新增的 `any`？
- 公共函数的输入、输出是否清晰？
- 联合类型是否做了完整性检查？
- 类型工具是否让调用方更简单？
