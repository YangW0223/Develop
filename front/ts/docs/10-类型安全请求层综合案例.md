# 10. 综合案例：类型安全的请求层

这一章把泛型、`unknown`、类型收窄、可辨识联合和映射类型组合起来。完整可运行代码位于 [type-safe-api.ts](../examples/type-safe-api.ts)。

## 1. 目标

我们希望调用请求函数时：

- 路径只能是已经定义的接口。
- 每条路径自动得到正确的响应类型。
- HTTP 失败和数据格式错误必须被调用者处理。
- 外部 JSON 在验证前保持 `unknown`。

## 2. 定义业务模型

```ts
interface User {
  id: number;
  name: string;
}

interface Product {
  id: number;
  title: string;
  price: number;
}
```

## 3. 建立“路径到响应”的映射

```ts
interface ApiSchema {
  "/users": User[];
  "/products": Product[];
}

type ApiPath = keyof ApiSchema; // "/users" | "/products"
```

`ApiSchema[P]` 可以根据路径 `P` 取得对应响应类型，这是索引访问类型在实际项目中的用法。

## 4. 不用异常表示预期失败

```ts
type ApiError = {
  kind: "http" | "invalid-data";
  message: string;
};

type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: ApiError };
```

当调用成功时才有 `data`，失败时才有 `error`。调用者检查 `ok` 后，TypeScript 会自动收窄。

## 5. 为每个端点提供运行时解析器

类型会在编译后消失，因此仅有 `ApiSchema` 还不够。我们需要真正检查 JSON 的函数：

```ts
type Parser<T> = (input: unknown) => T | undefined;

type Parsers = {
  [P in keyof ApiSchema]: Parser<ApiSchema[P]>;
};
```

`Parsers` 是映射类型：它要求每个 API 路径都存在解析器，而且解析结果必须和路径响应一致。新增接口后，如果忘了补解析器，编译器会立即报错。

## 6. 泛型请求函数

```ts
async function apiGet<P extends ApiPath>(path: P): Promise<Result<ApiSchema[P]>> {
  const response = await fetch(path);

  if (!response.ok) {
    return {
      ok: false,
      error: { kind: "http", message: `HTTP ${response.status}` },
    };
  }

  const raw: unknown = await response.json();
  const data = parsers[path](raw);

  if (data === undefined) {
    return {
      ok: false,
      error: { kind: "invalid-data", message: "响应格式不正确" },
    };
  }

  return { ok: true, data };
}
```

`P` 同时连接参数与返回值：传 `"/users"` 得到 `Result<User[]>`，传 `"/products"` 得到 `Result<Product[]>`。

## 7. 调用端获得精确类型

```ts
const result = await apiGet("/users");

if (result.ok) {
  result.data.forEach(user => console.log(user.name));
} else {
  console.error(result.error.kind, result.error.message);
}
```

调用者不能忘记失败分支，也不能把用户当成商品。路径、运行时校验和返回类型由同一映射连接起来。

## 8. 案例中各知识点的作用

| 知识点 | 作用 |
| --- | --- |
| `keyof` | 提取合法路径联合类型 |
| 泛型约束 | 保证请求路径属于 API 定义 |
| 索引访问类型 | 根据路径计算返回类型 |
| 映射类型 | 为每个接口强制提供对应解析器 |
| `unknown` | 防止未验证的 JSON 被直接使用 |
| 可辨识联合 | 明确区分成功与失败 |
| 类型收窄 | 检查 `ok` 后安全读取对应字段 |

## 9. 真实项目如何扩展

实际请求层还会处理请求参数、请求体、认证、取消、超时和不同错误结构。可以把 schema 扩展为：

```ts
interface Endpoint<Request, Response> {
  request: Request;
  response: Response;
}

interface FullApiSchema {
  "/users": Endpoint<{ page: number }, User[]>;
  "/products": Endpoint<{ keyword?: string }, Product[]>;
}
```

不过不要一次构造过于复杂的抽象。先让两三个真实端点工作，再抽取稳定的共同部分。

## 10. 练习

1. 新增 `/profile` 端点并定义单个用户响应。
2. 为错误增加 `network` 分支，并在 `fetch` 抛错时返回它。
3. 给每个端点增加请求参数类型，让参数也随路径变化。
4. 把手写解析器替换为 schema 校验库，并保持调用端类型不变。
